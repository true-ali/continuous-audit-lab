# Methods

This document describes what the code in this repository does, module by module. Every number
below is either a constant in the code or a measured result from a run on the synthetic ledger
(seed 42, default settings). Nothing here has been validated against labelled real-world fraud,
and the real public data has no labels, so no accuracy claim is made for it.

Source of the payment data: South Lakeland District Council, payments to suppliers over 250,
published under the Open Government Licence. The synthetic ledger is generated by the code and
has no link to any real supplier or payment.

## 1. Pipeline overview

| Step | Command (Makefile) | Module | What it does |
|---|---|---|---|
| Download | `make data` (part 1) | `data/download.py`, `scripts/download_data.py` | Reads the CSV list from the publisher's CKAN metadata, checks sizes with HEAD requests before downloading, refuses total size above 500 MB unless `--force`, writes a SHA-256 manifest, skips files whose hash already matches. |
| Prepare | `make data` (part 2) | `data/loader.py` | Maps raw CSV headers to the canonical schema, parses amounts and dates, assigns `txn_id` from row order, writes `data/processed/payments.csv` and `data/processed/quality_report.json`. |
| Synthetic | `make synth` | `data/synthetic.py` | Generates a seeded ledger with labelled anomalies and writes `data/processed/synthetic.csv`. |
| Run | `make run` (synthetic) or `python -m continuous_audit_lab.cli run --source real` | `monitor/runner.py` | Runs every month in order with no look-ahead, writes alerts, evidence records, KRIs and thresholds to `runs/audit.duckdb`. |
| Report | `python -m continuous_audit_lab.cli report` | `cli.py` | Prints latest KRIs with RAG status and the alert total. On synthetic runs it also prints the backtest table. |
| Dashboard | `make dashboard` | `dashboard/app.py`, `dashboard/data.py` | Streamlit view over the DuckDB run output. |

Canonical schema (`data/schema.py`): `txn_date`, `supplier`, `amount`, `expense_type`,
`department`, `reference`, plus `txn_id`. The synthetic data also carries `anomaly_type`, which is
empty for clean rows and is the only source of labels. The real data has no such column.

## 2. The eight SQL tests (`tests_sql/*.sql`)

The SQL files are the audit tests. Each one reads a DuckDB table named `payments`, and `$name`
placeholders are filled from `tests_sql/params.py` (`DEFAULT_PARAMS`, parameter version `v1`).
`tests_sql/runner.py` keeps only the parameters a file actually uses, because DuckDB rejects
unused ones.

Six tests are **row-level**: each finding lists the transaction ids it flags, and these feed the
risk score and the KRIs. Two are **aggregate**: they return per-month metrics, not finding lists.

Parameter values below are the defaults in `params.py`. All of them are assumptions.

### 2.1 duplicate_payments (row-level)

- **What:** exact duplicates (same supplier, amount and non-empty reference) and near duplicates
  (same supplier, amount, expense type and department, with each payment within
  `duplicate_window_days` of the previous one, chained into clusters).
- **Why:** a payment posted twice is a classic overpayment or fraud pattern.
- **Params:** `duplicate_window_days` = 5.
- **Clustering:** consecutive payments whose gap is at most the window form one cluster. Because
  of chaining, a cluster can span longer than the window overall. A cluster made only of one
  non-empty reference is reported once, by the exact branch.
- **Flagged value:** amount times (copies minus one), i.e. the redundant copies.
- **Known false positives (from the file header):** fixed-fee invoices such as rent, licences and
  subscriptions paid twice for legitimate reasons; genuine repeat orders at the same price;
  suppliers reusing reference numbers across unrelated invoices.

### 2.2 threshold_splitting (row-level)

- **What:** three or more payments to one supplier, each between 80% and 100% of the same approval
  limit, within 7 days, whose total reaches the limit, and whose count is at least 4 times the
  count the supplier would be expected to produce in that band over the same window.
- **Why:** splitting a purchase so that each part needs only the lower approval.
- **Params:** `approval_limit_1/2/3` = 1,000 / 5,000 / 10,000 (assumptions, not any organisation's
  real limits); `split_lower_ratio` = 0.80; `split_min_payments` = 3; `split_window_days` = 7;
  `split_excess_ratio` = 4.0.
- **Expected rate:** the supplier's band share is its band payments divided by all its payments in
  the ledger passed to the test. Inside the monitor that ledger is cut off at the end of the scored
  month (see section 7), so the expectation uses only earlier data plus the current month. A
  standalone run on the full synthetic file uses all 36 months and is therefore not causal.
- **Clustering:** each band payment with no earlier band payment of the same supplier and limit in
  the window is an anchor; the cluster is the anchor plus later band payments in the window, so each
  cluster is reported once.
- **Flagged value:** total of the cluster.
- **Known false positives:** deliberate milestone billing just under a limit; a low-volume supplier
  with a genuine burst of invoices in the band.

### 2.3 round_amounts (row-level)

- **What:** (a) a single payment that is an exact multiple of 1,000 and at least 1,000; (b) three or
  more payments to one supplier of the same amount at or above 1,000 in one calendar month.
- **Why:** round lump sums often mean estimates or unsupported amounts. The file header states that
  this is a weak signal on its own.
- **Params:** `round_modulus` = 1,000; `round_min_amount` = 1,000; `round_min_count` = 3.
- **Known false positives:** genuine fixed-price contracts, deposits, rent and retainers. The test
  does not look at a supplier's share of round payments, so a supplier whose prices are mostly
  round is flagged on every payment.

### 2.4 off_hours (row-level)

- **What:** payments dated on a Saturday or Sunday, or with a time before 07:00 or at/after 19:00.
- **Why:** postings when no approver is normally working can indicate unauthorised disbursement.
- **Params:** `business_hour_start` = 7; `business_hour_end` = 19.
- **Date-only data:** if every `txn_date` is at midnight, the hour check is skipped and only weekends
  are flagged.
- **Known false positives:** public holidays are not modelled; genuine out-of-hours work such as
  month-end close, overseas suppliers and automated batch runs.

### 2.5 dormant_reactivation (row-level)

- **What:** a payment to a supplier whose previous payment was at least 9 months earlier, where the
  supplier has at least 5 earlier payments, and where the amount exceeds the 95th percentile of that
  supplier's earlier payments. Only earlier rows (ordered by date then txn_id) are used.
- **Why:** a long-silent supplier that suddenly receives a large payment can be a fictitious or
  hijacked vendor account.
- **Params:** `dormant_months` = 9; `dormant_min_history` = 5; `dormant_history_quantile` = 0.95.
- **Known false positives:** contracts resuming after a seasonal or project pause; annual or
  milestone payments; suppliers whose first ledger payment has no history.

### 2.6 reference_integrity (row-level, partly)

- **What:** (1) a non-empty reference used by more than one supplier, or by one supplier with more
  than one distinct amount; one finding per reference. (2) For references of the form
  `PREFIX-NNNNNN`, missing numbers between consecutive sequence numbers of the same prefix; one
  finding per prefix.
- **Why:** a reused reference can hide a second payment under an existing invoice; gaps can indicate
  voided or unrecorded invoices.
- **Params:** none.
- **Limit of the design:** sequence-gap findings list no transaction ids, so they do not add anything
  to the per-payment risk score or to the flagged-value KRIs. Only the reused-reference branch feeds
  the score.
- **Synthetic data:** the synthetic references are one unbroken sequence, so the gap branch is not
  exercised. The test only checks that the query runs there (section 6).

### 2.7 benford_first_digit (aggregate)

- **What:** for each month and for each expense type, the observed first-digit distribution of
  positive amounts compared with the expected Benford distribution `log10(1 + 1/d)` for d = 1 to 9.
  The statistic is the mean absolute deviation (MAD) across the nine digits.
- **Grades:** `insufficient_data` below `benford_min_rows` (300) positive amounts, and no MAD is
  reported for those groups. Otherwise: MAD <= 0.006 `close`; <= 0.012 `acceptable`; <= 0.015
  `marginal`; above 0.015 `nonconforming`.
- **Source status of the bands:** the first three cut-offs (0.006, 0.012, 0.015) are the ones
  quoted from Nigrini (2012) in the file header. The cut-off above 0.015 was **not independently
  verified** in this repository. It is taken from the cited source as recalled and must be checked
  against the source before anyone relies on the `nonconforming` label.
- **Why MAD and not chi-square:** a chi-square test rejects conformity almost always on a large
  ledger, because its power grows with the number of rows, so trivial deviations become
  "significant". MAD measures the size of the deviation and does not scale with n, so it is used
  here to grade conformity. Chi-square is therefore not used in this repository at all.
- **Where it does not apply:** bounded amounts (all between 5,000 and 5,999, for example), fixed or
  assigned fees, amounts capped at an approval limit, mostly round amounts, small samples, and
  months or types dominated by one recurring supplier. A nonconforming grade there is weak evidence.
- **Use in the monitor:** only the `all` scope MAD is a KRI (`benford_mad`).

### 2.8 supplier_concentration (aggregate)

- **What:** per month and expense type: total positive value, number of suppliers, largest supplier
  share (`top_share`), and the Herfindahl-Hirschman Index `HHI = sum(share^2)` on a 0 to 1 scale.
- **Reading:** HHI runs from 1/n (equal shares across n suppliers) to 1.0 (one supplier). A category
  with few suppliers has a high HHI naturally, so `n_suppliers` must be read with it. Compare a
  category with its own history, not with other categories.
- **Params:** none. Negative amounts (credits and reversals) are excluded.
- **Use in the monitor:** the KRI `supplier_hhi` is the HHI of each expense type, averaged for the
  month and weighted by each type's paid value.

## 3. Statistical scoring (`scoring/stats.py`)

`stat_scores(payments, month)` returns three scores per payment in the month. Every score uses only
rows dated before the first day of the month, with the exception of per-transaction history features,
which look only at earlier rows in (date, txn_id) order.

Constants: `MIN_BASELINE_ROWS` = 20; `MIN_SUPPLIER_HISTORY` = 5; `DEFAULT_WINDOW_MONTHS` = 12;
`MAD_SCALE` = 0.6745; `IFOREST_ESTIMATORS` = 100; `SUPPLIER_WINDOW_DAYS` = 30;
`NO_HISTORY_DAYS` = 365; `MIN_AMOUNT` = 0.01.

### 3.1 Robust z-score

`robust_z(x, median, MAD) = 0.6745 * (x - median) / max(MAD, 1e-9)`.

Scores are computed on the log of the amount. Median and MAD are used instead of mean and standard
deviation because a few large payments would otherwise inflate the spread and hide themselves. The
constant 0.6745 makes the score comparable to a standard z-score under a normal assumption.

- **z_expense:** the amount against the median and MAD of its expense type, over the previous 12
  months. If the expense type has fewer than 20 baseline rows, the score is set to 0.
- **z_supplier:** the amount against the median and MAD of the same supplier, over all earlier
  months. If the supplier has fewer than 5 earlier rows, the score is set to 0.

### 3.2 Per-supplier deviation

`z_supplier` is the per-supplier deviation described above. It is separate from `z_expense` so that a
payment can be unusual for its supplier even when it is ordinary for its category, and the reverse.

### 3.3 Isolation Forest

`IsolationForest(n_estimators=100, random_state=seed)` is fitted on the 12-month expense baseline
only, never on the month being scored. The features, in fixed order (`IFOREST_FEATURES`):

| Feature | Why it is included |
|---|---|
| `log_amount` | Lognormal spend profiles become roughly symmetric on a log scale. |
| `days_since_last` | Long dormancy and very rapid repeat payments both stand out. Default 365 for a first payment. |
| `count_30d` | Number of payments to the same supplier in the 30 days before this one. Bursts of small payments show up here. |
| `weekday` | 0 (Monday) to 6 (Sunday). Weekend postings are an off-hours signal. |
| `z_expense` | Gives the forest the category context that raw size does not. |

The score is an empirical percentile: the share of baseline rows whose forest anomaly score is lower
than the target's. It is 0 for the most ordinary rows and close to 1 for the most unusual. If the
baseline has fewer than 20 rows, every score is 0.

Note: the baseline percentile reference is computed on the same baseline rows the forest was fitted
on, so it is in-sample. This is a known simplification, not a held-out calibration.

## 4. Transparent risk score (`scoring/risk.py`)

`score_month` produces a weighted sum. Each component is scaled to 0 to 1 and then multiplied by its
weight, so the weight is the largest amount that component can add.

| Component | Weight (max contribution) | Source |
|---|---|---|
| duplicate_payments | 3.0 | row-level flag (0 or 1) |
| threshold_splitting | 3.0 | row-level flag |
| dormant_reactivation | 3.0 | row-level flag |
| reference_integrity | 2.0 | row-level flag |
| round_amounts | 1.0 | row-level flag |
| off_hours | 1.0 | row-level flag |
| z | 0.5 | `min(max(abs(z_expense), abs(z_supplier)), 6) / 6` |
| iforest | 1.0 | forest percentile, clipped to 0 to 1 |

The maximum possible score is therefore 3 + 3 + 3 + 2 + 1 + 1 + 0.5 + 1 = 14.5.

- Weights are **judgement-based assumptions** chosen to reflect how strong each flag is in audit
  practice. They were not fitted to labelled data, so the score is **not a calibrated probability**.
- Ranks run from 1 (riskiest) down. Ties are broken by ascending `txn_id`, so the order is
  deterministic.
- `risk_reasons` lists the components whose weighted contribution is at least 0.5.
- Row-level flags come from `scoring/rules.py`. For each scored month, the six row-level SQL tests are
  run on the ledger cut off at the end of that month, and only findings whose period is that month
  count. Every listed transaction id dated in the month is marked as flagged.

## 5. Evaluation protocol (`scoring/evaluate.py`)

The evaluation applies only to the synthetic ledger, because only it has labels (`anomaly_type`).

- **Warm-up:** the first 12 months are skipped so that every evaluated month has a full history
  window. On the default 36-month ledger, 24 months are evaluated.
- **Rankers:** `risk_score` (the score above), `amount_only` (amount descending, ties by txn_id),
  and `random` (a permutation drawn from a generator seeded with 0, so results repeat exactly).
- **Precision@k:** hits in the top k divided by k.
- **Recall@k:** hits in the top k divided by the month's number of anomalies. It is NaN for months
  with no anomalies and those months are left out of the recall average, not counted as zero.
- **k:** 50 by default, which is also the default number of alerts per month in the monitor.
- **Summary:** mean precision and mean recall per ranker, with the number of months and of months
  that have anomalies.

Measured on the synthetic ledger (seed 42, defaults):

| Ranker | precision@50 | recall@50 |
|---|---|---|
| risk_score | 0.153 | 0.946 |
| amount_only | 0.077 | 0.471 |
| random | 0.021 | 0.117 |

Over 24 evaluated months with about 8.4 injected anomalies a month, precision@50 is capped near
0.17 (8.4 / 50), because a month cannot contain more hits than it has anomalies. Read precision@50
against that ceiling, and read recall@50 with the anomaly counts in mind: recall is high partly
because each month has few anomalies. See `LIMITATIONS.md` for why these numbers are optimistic.

## 6. Tests and what they cover

Tests live in `tests/` and run with `make test` (pytest). Coverage by file:

- `test_sql_dup_split_round.py`: recall on labelled duplicate, splitting and round anomalies (target
  at least 0.8); no duplicate findings and few threshold findings (limit 5) on clean data; round flags
  rare on clean data (below 1%); output columns.
- `test_sql_hours_dormant_refs.py`: off-hours recall; dormant recall; reference_integrity runs; clean
  data gives no findings for the off-hours and dormant tests; no reused-reference findings on clean
  data; dormant test ignores later rows.
- `test_sql_benford_hhi.py`: lognormal amounts conform; narrow uniform band is nonconforming; small
  month is insufficient_data; HHI equals 0.5 for two equal suppliers and 1.0 for one supplier.
- `test_scoring_stats.py`: robust z against a hand example; one row per transaction; rows from the
  next month do not change scores; injected anomalies score higher than clean rows; a time budget.
- `test_scoring_risk.py`: precision@k and recall@k definitions; `rule_flags` does not use future rows;
  ranks are unique; weights cover every row-level flag; risk precision@50 beats both baselines on the
  synthetic ledger.
- `test_kri.py`: thresholds against a hand calculation on 1 to 12; scaled MAD floor; RAG boundaries;
  baseline labelling; thresholds ignore later months; KRIs finite for a late month.
- `test_monitor.py`: repeated runs give an identical run log; one log row per month; every alert
  re-performs and detects a changed amount; thresholds ignore the last months of data; a month's
  alerts do not depend on later months.
- `test_synthetic.py`: same seed gives identical output; different seed differs; txn_id sequential;
  every anomaly type injected; no anomalies in the baseline year; clean references unique.
- `test_loader.py`: header detection and amount/date parsing; bad rows kept as NaN and counted;
  unmappable file flagged; quality report totals.
- `test_download.py`: second run downloads nothing; manifest checksums match; dry run downloads
  nothing.
- `test_dashboard.py`: KRI tiles, alert loading, transaction view, and that the app renders.

The tests that check clean-data false positives and recall use the synthetic generator, so they show
the tests fire on the patterns the generator injects. They do not show performance on real data.

## 7. No-leakage design

"Leakage" here means a score for month t using information from month t+1 or later. The design
prevents it in four places:

1. **Rule flags** (`scoring/rules.py`): each month's row-level tests run on the ledger cut off at the
   end of that month (`txn_date < month + 1 month`).
2. **Statistical scores** (`scoring/stats.py`): the expense baseline and the forest use only rows dated
   before the month. Supplier history features look only at earlier rows in (date, txn_id) order.
3. **Dormancy and history** (`dormant_reactivation.sql`): the earlier-history window is
   `ROWS BETWEEN UNBOUNDED PRECEDING AND 1 PRECEDING`.
4. **KRI thresholds** (`monitor/kri.py`): `build_thresholds` reads only the first `warmup_months` rows.
   Later months are judged against fixed limits and cannot move them.

How it is tested:

- `test_rule_flags_do_not_use_future_rows`, `test_stat_scores_ignores_rows_dated_from_next_month`,
  `test_dormant_reactivation_ignores_later_rows`: changing or adding later rows does not change an
  earlier score.
- `test_thresholds_ignore_months_after_baseline`, `test_thresholds_ignore_the_last_months_of_data`:
  the limits do not move when later months change.
- `test_alerts_of_a_month_do_not_depend_on_later_months`: the alerts for a month are the same when
  later months are removed.

Known gap: the `threshold_splitting` header describes its expectation as "over the whole ledger". In
the monitor that ledger is the cut-off ledger, so the expectation is causal. A standalone call on the
full file is not, and the code does not prevent that call.

## 8. KRIs and RAG thresholds (`monitor/kri.py`)

Seven monthly KRIs, each one number per month:

| KRI | Definition |
|---|---|
| flagged_share | Distinct payments flagged by any row-level test, divided by payments in the month. |
| flagged_value | Sum of amounts of those flagged payments. |
| duplicate_value | Sum of `flagged_value` of the duplicate_payments findings. |
| near_threshold_clusters | Count of threshold_splitting findings. |
| benford_mad | MAD of the `all` scope in benford_first_digit; NaN if no grade. |
| supplier_hhi | HHI per expense type, averaged across types and weighted by paid value. |
| dormant_reactivations | Count of dormant_reactivation findings. |

**Thresholds.** For each KRI, using only the first 12 months by default:

- `median` is the typical level.
- `scaled_mad` = max(1.4826 x MAD around the median, floor). The factor 1.4826 makes the scaled MAD
  comparable to a standard deviation under a normal assumption.
- Amber = median + 2 x scaled_mad. Red = median + 3 x scaled_mad (a control-chart convention).

Per-KRI floors on the scaled MAD (`MIN_SCALE`): flagged_share 0.01; flagged_value 1,000;
duplicate_value 1,000; near_threshold_clusters 1; benford_mad 0.002; supplier_hhi 0.01;
dormant_reactivations 1. The floor stops a flat baseline from turning every small positive value red.

**RAG.** A value at or above red is `red`; at or above amber is `amber`; otherwise `green`. A missing
value or limit is `n/a`. The first 12 months are labelled `baseline`, because they set the thresholds
and their status is not a judgement.

**Calibration artefact on synthetic data.** The synthetic baseline has no injected anomalies, so the
median of `flagged_value` is 0 and its MAD is 0. The 1,000 floor then sets amber at 2,000 and red at
3,000. Measured result: `flagged_value` is red in all 24 post-baseline months. This is an effect of
the assumption and the clean baseline, not a finding about the data. The thresholds are assumptions,
not validated limits, and should be reviewed against investigation outcomes.

## 9. Evidence store and re-performance (`monitor/evidence.py`, `monitor/runner.py`)

Each alert is the top 50 payments of a month with a positive risk score. Each alert record holds
`alert_id` (run id, period, txn id), `risk_score`, `rank` (the rank within the month), `risk_reasons`,
`tests_fired`, `involved_txn_ids`, `params_json`, `evidence_hash` and `amount`.

- `tests_fired`: the row-level tests that list this transaction for the month.
- `involved_txn_ids`: the transaction plus every id those tests list.
- `evidence_hash`: SHA-256 over canonical JSON of `{tests_fired, params, rows}`, where `rows` are the
  canonical fields (txn_id, date, supplier, amount, expense type, department, reference) of the
  involved transactions, sorted by txn_id.
- `params_json`: the parameters, the parameter version and the weights. The weights are stored but are
  **not** part of the hash.

**Re-performance** (`reperform`): re-reads the involved rows from the source ledger, recomputes the
hash with the stored tests and parameters, and re-runs the fired tests on the ledger cut off at the
alert's month. The result is True only if the hash matches and every fired test still lists the
transaction. An alert that fired no row-level test skips the re-run and is checked by hash only. In
that case the risk score itself is not re-performed.

The run writes these DuckDB tables, rebuilt from scratch on each run: `run_log`, `alerts`, `kris`,
`kri_thresholds`, `kri_rag`, `data_quality`, `run_meta`. The `run_id` is a hash of the ledger, the
parameter version, `alert_k` and the source, so equal inputs give equal ids. `run_log` stores a
per-month data hash and the list of tests executed.

## 10. Benford and why chi-square is not used

Benford's law gives the expected first-digit frequencies for many naturally occurring numbers. The
test here compares observed and expected frequencies with MAD (section 2.7). Chi-square would be the
textbook test, but on a large ledger it rejects almost any real population,
because the test statistic grows with n. A small, practically irrelevant deviation then looks like
strong evidence. MAD measures how far the distribution is from Benford, not whether the difference
could be chance, so it is the more useful number for ranking months and groups. The price is that the
bands are rules of thumb with no analytic critical value.

## 11. Data loading (`data/loader.py`, `data/download.py`)

- The header is searched in the first 15 lines. A header is accepted when it maps to `txn_date`,
  `supplier` and `amount` (aliases in `HEADER_ALIASES`).
- Amounts: `£`, commas and spaces are removed; a value in parentheses is negative; unparseable
  amounts become NaN.
- Dates: parsed against an explicit list of formats (day-first UK formats and ISO). Pandas' day-first
  parsing is not used, because it misreads ISO dates.
- Rows with unparseable amounts or dates are kept as NaN and counted in the quality report, so no source
  row disappears silently. How the downstream tests treat NaN amounts or dates was not separately verified.
- Files without a recognisable header are skipped and listed in the quality report.
- Output: `data/processed/payments.csv` (the code writes CSV because `pyarrow` is not a dependency, even
  though the default path name is `.parquet`) and `data/processed/quality_report.json`.
- Downloads use a HEAD pass for total size, a 500 MB guard, `.part` files renamed on completion, and a
  SHA-256 manifest so re-runs fetch only missing or corrupted files.
